## 把做了一半的项目，交给一支 AI 团队。

把半成品交给首席，途中改一个要求。生产官接着做，审核官打开成品查错，首席把通过审核的版本交回原对话。

**一套备品已经按计划领用。散场时应交回几套？** 生产初稿 R1 — 仍要求交回 1 套。 交付版 R2 — 应交 0 套，记桌号和时间。

WorkBuddy 合成活动题的两版表格。依据为团队本机观察及留件，未取得平台端运行日志。 [看一次真实退修](proof/README.md)

## 你用哪个平台？

选你已有可用模型的平台。每种入口先跑首席、生产官和审核官三席。

### Grok Bot

已有三席就复用；初次使用按包内岗位卡逐席建立。 [打开三席首单包](adapters/grok/first-order.zip)

现有团队接过 20→24 人变更。督导指出一处交接问题，原团队修订、复核后在首席原对话交回 R2。尚无统一全队导入实证。

### OpenMausBot

从「模板 → 导入」选择团队文件。先看有无同名部门；重复添加会多出一套。 [取三席团队文件](adapters/openmaus/team.openmaus.json) · [读导入说明](adapters/openmaus/README.md)

首单使用在本机手动建立的三席，独立审核后交回双附件，期间批准过一次目录操作。下载的部门文件已在隔离存储用宿主原生函数导入、导出；尚未在真实账号界面点击导入该文件。发单前请逐席核对批准设置。

### WorkBuddy

配套安装器仅适用于 macOS 上的 WorkBuddy 5.9.3，尚无 Apple 公证。打开安装说明，按本机情况选用入口，再为这单选择工作文件夹。 [打开安装与预览说明](adapters/workbuddy/README.md) · [打开可点选的两个离线入口](adapters/workbuddy/start.html)

随附 0.1.0 原件在已配置的私有三席团队跑通首单。一次定向退修后，审核席重新打开 R2，首席交回成品与审核记录。原件中的示例支持邮箱仅作占位，请勿联系。

### DeepSeek Harness

解压标准 project.zip，找到并列的「一人成阵-DSH」和「试用者第二步」。在 Harness 的工作区选择器中点进「一人成阵-DSH」，选这个目录本身；它里面有 inputs 和隐藏的 .dsh。不要选外层解压目录或 .dsh。新会话键入 / 选 solo-to-team。首席确认接单后，再从旁边的「试用者第二步」取变更卡。 [取标准项目包](adapters/deepseek/project.zip) · [DS Bot v0.3.2 长期席位引导包（建队尚待实机验证）](adapters/deepseek/ds-bot-guide.zip)

若 ZIP 是你用建队器导出的，请先新建专用空目录，将 ZIP 内容直接解压到其中，选择这个含 team.definition.json 和 .dsh 的目录为工作区。

已配置的本机标准组用项目技能分别派出生产和审核子任务。本机测试观察与逐版文件记录了六次退修。R7 零阻断、五条建议，首席原会话交回两份可打开的附件。云端复核范围限于交件。普通外部用户独立上手尚未实测。

## 怎么开第一单

1. **交半成品**　把根目录 brief/01-intake.md 这份 20 人活动底稿交给首席，请它确认版本与已定条件。固定入口包内旧题也可用。 [打开根目录活动底稿](brief/01-intake.md) · [交件检查](delivery-check/README.md)：成果若写了日期，来源是哪条输入？没有就写日期待定。变更是否同步到受影响的通知？ 日期与下游通知的检查提示只补入根目录这份中英底稿；此前实跑用的是补句前的版本。

2. **中途改要求**　等首席报出底稿版本，再在同一对话发 24 人变更。原定场地、预算上限和时段继续有效。 [打开变更单](brief/02-change.md)

3. **在原处收件**　亲自打开首席交回的执行包和独立审核记录。核对两份指向同一版本、变更已落进表格，退修项已有处理结论。

## 再试一单：社区维修预约

先给首席[四单维修预约](examples/maintenance/01-intake.md)。等它确认底稿，再给[北楼临时封闭的变更](examples/maintenance/02-change.md)。收件时用同一份新版核排程和受影响站点的通知草稿。交件后再看[本次结果对照](examples/maintenance/outcome.md)。

## 这三席背后还有什么

<details><summary>建队器的自定义岗位验证到哪一步？</summary>

建队器核对生产与独审的席位 ID 是否不同。两席背后是否同一操作者、审核是否实际独立，要看运行记录和审核席打开的成品。

固定首单包与用户导出的岗位包是两份不同的文件，各自核收。自定义 DeepSeek 样例改名并新增一席后，据团队本机观察，使用当前这版建队器导出的项目在本机宿主运行；界面显示 3 个子任务，留有岗位分工、审核记录和第四席回件。云端复核未取得平台运行日志。自定义 OpenMausBot 四席部门文件已用 0.1.148 的实际数据层在隔离存储导入；用户真实账号界面跑单尚未实测。两项的回执和导入记录留在团队侧，未放入本包，读者无法在包内复核。
